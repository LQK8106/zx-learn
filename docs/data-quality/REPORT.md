> 评估日期：2026-11-21
> 工作目录：`output/data-quality/`
> 证据目录：`result/`（全部数字由 `sql/` 下脚本实际执行产生，未使用估算值）

## 1. 评估对象与范围

### 1.1 数据集与来源

| 项 | 内容 |
|---|---|
| 数据集 | Brazilian E-Commerce Public Dataset by Olist（Olist 巴西电商公开数据集） |
| 原始发布 | Kaggle 公开数据集 |
| 本次下载 | GitHub 公开镜像 `olist/work-at-olist-data` 的 `datasets/` 目录（8 个 CSV，逐个校验 HTTP 200 后下载） |
| 许可 | **CC BY-NC-SA 4.0**：允许署名引用与二次分析，**禁止商业使用**，衍生作品需同许可共享 |
| 纳入表 | 8 张：orders、customers、order_items、payments、reviews、products、sellers、category_translation |
| 总行数 | **550,759 行**（8 张表行数之和，见 `result/00-profile.csv`） |
| 时间跨度 | 下单 2016-09-04 至 2018-10-17；评价创建 2016-10-02 至 2018-08-31（见 `result/00-profile-3.csv`） |
| 数据性质 | 已匿名的真实交易数据；评论文本中的公司名被替换为虚构名称 |

### 1.2 为什么选它

框架的首选是省市级公共数据开放平台的政务数据集，并要求通过四项预检。实际预检结果：在可用时间内，未找到同时满足「≥2 张表可用外键关联、免实名直接下载、许可允许公开二次分析、单表≥1 万行」四项条件的政务数据集，因此按框架规则退到候选 B（Olist）。

这是一个明确的取舍：业务域是电商而非政务，但 8 张表之间主外键清晰，六维中的完整性、一致性、唯一性、有效性都能做跨表规则判定，方法可迁移。报告不把「电商」包装成「数据要素」，只陈述测了什么、怎么测。

### 1.3 明确不评估什么

- **不评估 geolocation 表**：原始数据集含约 61MB 的经纬度表，本次未下载，因此不做坐标合法性与「CEP→坐标」映射校验；CEP 只做格式校验。
- **不评估评论文本的语义质量**：不做情感分析、不判断评论内容是否真实。
- **不评估「数据是否与客观现实一致」的全量准确性**：没有权威主数据可供比对，准确性维度仅覆盖规则可判定部分（见第 2 节与第 9 节）。
- **不评估实时性与平台性能**：这是一次离线快照评估，不涉及吞吐、并发、查询延迟。
- **不评估 2018 年之后的市场状况**：数据快照距今 2,957 天（约 8.1 年，见 `result/05-timeliness-2.csv`）。

## 2. 方法与口径

### 2.1 六维定义与判定强度

| # | 维度 | 定义 | 本次核心指标 | 判定强度 |
|---|---|---|---|---|
| 1 | 完整性 | 该有的数据是否存在 | 字段缺失率、履约节点缺失率、**引用完整性孤儿率** | 规则可判定（强） |
| 2 | 一致性 | 同一事实在不同位置是否冲突 | 跨表金额勾稽、状态与时间戳顺序、同实体属性冲突 | 规则可判定（强） |
| 3 | 唯一性 | 同一实体是否被重复表达 | 主键重复率、业务键重复率 | 规则可判定（强） |
| 4 | 准确性 | 值是否与客观真实相符 | 负值/零值、值域越界、未来日期 | **仅部分可判定（弱）** |
| 5 | 及时性 | 数据是否在需要时可用 | 事件时间→入库时间延迟 | 需要双时间戳；**本次不可测** |
| 6 | 有效性 | 格式与取值是否符合约定 | 格式正则、枚举白名单、日期可解析率、码表命中率 | 规则可判定（强） |

**准确性声明**：本维度仅覆盖规则可判定部分，未与权威主数据比对，**不代表整体准确率**。

**及时性声明**：数据中不存在 ingest/load/etl/created_at/updated_at 一类入库时间字段（探测结果 0 行，见 `result/05-timeliness.csv`），只有业务事件时间，因此无法计算「事件→入库」延迟。本报告不构造替代指标，**及时性不计分**，仅在 4.6 与第 9 节说明可观测到的快照陈旧度与业务处理时长。

### 2.2 数据装载与空值界定

- 8 个 CSV 先以 **全 VARCHAR** 装入 `*_raw` 表，保留原始字符（尤其是邮编这类可能丢失前导零的字段），再建立带 `TRY_CAST` 的类型化视图供规则使用。
- **空值**：日期/数值列按 `IS NULL` 计；文本列按 `IS NULL OR TRIM(col) = ''` 计。未把 `'-'`、`'0'` 额外当作空值。
- **零值**不混入缺失率，而在准确性维度单独判定（A02 支付金额 <=0、A04 重量/尺寸 <=0），避免「空值」与「可疑值」口径混淆。
- **浮点容差**：所有金额比较统一用 `ABS(a - b) > 0.01`，不使用 `<>`。

### 2.3 评分算法与权重声明

- 每维内各规则**等权**：维度得分 = `100 − 该维各规则违规率的算术平均`。
- 综合得分 = 各维度得分按权重加权后归一化。
- **权重为自设**：完整性 25%、一致性 25%、唯一性 15%、准确性 10%、有效性 15%、及时性 10%。由于及时性不可测，其 10% 权重被剔除，其余五维按 90% 归一化。
- **本权重为自设，用于排序改进优先级，不代表行业基准。**

### P1 订单金额勾稽不一致（高）

**现象**：把同一订单的 `order_items.price + freight_value` 之和与 `payments.payment_value` 之和比较，容差 0.01，366 单不一致，占 98,665 个可比订单的 0.37%。

**影响面**：
- 绝对差额合计 7,978.74，单笔最大差额 336.93。
- 方向：支付大于明细 269 单，明细大于支付 97 单。
- 构成：仅 20 单有多笔支付，10 单含 voucher，73 单有多条明细。也就是说，**voucher 拆分只能解释少数样本**，大额差异双向存在，不能简单归因于「优惠券未入明细」。

**根因**：更接近源系统的金额录入/结算口径差异（分期手续费、部分退款、运费结算）而非单一 ETL 规则错误。现有字段不足以进一步区分，报告中不下确定性结论。

**证据**：`sql/02-consistency.sql`（K01）；`result/02-consistency.csv`；差异分桶 `result/02-consistency-2.csv`；构成 `result/02-consistency-3.csv`。

差异分桶（`result/02-consistency-2.csv`）：

| 差额区间 | 订单数 | 占可比订单 |
|---|---:|---:|
| ≤0.01（匹配） | 98,299 | 99.63% |
| 0.01–1 | 54 | 0.05% |
| 1–10 | 160 | 0.16% |
| 10–100 | 131 | 0.13% |
| >100 | 21 | 0.02% |
| 无支付记录 | 1 | 0.00% |

### P2 review_id 重复且跨订单冲突（高）

**现象**：99,224 行评价中，`review_id` 去重后少 814 行，重复率 0.82%。

**影响面**：
- 789 个重复 `review_id` 组，覆盖 1,603 行，多出 814 行，单组最多 3 行。
- **789 组全部跨不同订单**（`order_id` 冲突），组内评分无冲突（0 组）。
- 业务含义：同一 `review_id` 出现在不同订单上，说明它不能作为「一条评论」的唯一业务键；按 review_id 去重或关联会把不同订单的评价合并，按订单统计评价数则不受影响。

**根因**：ETL 键映射/去重逻辑缺陷（最可能），而非业务允许的一对多——正常的一对多应表现为同一订单多条不同 review_id，而不是同一 review_id 跨多个订单。

**证据**：`sql/03-uniqueness.sql`（U05）；`result/03-uniqueness.csv`；`result/03-uniqueness-2.csv`。

补充：每单评价条数分布为 1 条 98,126 单、2 条 543 单、3 条 4 单（`result/03-uniqueness-3.csv`），这部分是正常的一对多，不计为重复。

### P3 客户 CEP 前导零丢失（中）

**现象**：99,441 条客户记录中，23,995 条邮编前缀只有 4 位（24.13%），75,446 条为 5 位；卖家侧 1,027/3,095 条为 4 位（33.18%）。

**影响面**：按原始 CEP 关联或做地理聚合时，约四分之一的客户记录会落到错误的键上；若直接以「非 5 位」判无效，会把这批本可修复的记录全部丢弃。

**根因**：ETL/导出环节把邮编当作整数处理，前导零被截断。证据是补齐前导零后违规率降为 **0.00%**（`result/06-validity-2.csv`），说明字符本身合法，只是长度丢失。

**证据**：`sql/06-validity.sql`（V04）；`result/06-validity.csv`；长度分布 `result/06-validity-3.csv`；敏感性口径 `result/06-validity-2.csv`。

### P4 商品类目缺失/未翻译（中）

**现象**：32,951 个商品中，610 个类目为空（1.85%）；另有 13 个商品的类目不在翻译码表中（0.04%），其中 `portateis_cozinha_e_preparadores_de_alimentos` 10 个、`pc_gamer` 3 个。

**影响面**：类目维度的销售额/转化分析会出现「未知」桶；英文标签缺失只影响展示层，不影响葡语原值。

**根因**：610 条缺失更可能是源系统录入/上游遗漏；13 条属于**外部参照缺失**——翻译码表版本落后于商品目录。

**证据**：`sql/01-completeness.sql`（C07）、`sql/06-validity.sql`（V06）；`result/01-completeness.csv`、`result/06-validity.csv`、`result/06-validity-4.csv`。

### P5 同一 customer_unique_id 城市/州冲突（中）

**现象**：在 2,997 个「存在多条 customer_id 记录」的 `customer_unique_id` 组中，122 组出现城市或州不一致（4.07%）。

**影响面**：这是客户身份归并问题。按 `customer_unique_id` 去重时，需要选择「最新地址」或「主要地址」策略，否则地域统计会在 122 组上产生歧义。

**根因**：源系统录入（同一人多次下单填写不同地址）或业务上允许的地址变更。仅凭现有字段无法区分「搬家」与「录入错误」，因此不判为脏数据，只登记为口径风险。

**证据**：`sql/02-consistency.sql`（K05）；`result/02-consistency.csv`。

### P6 时间戳倒序与状态冲突（低）

**现象与影响面**：

| 规则 | 违规数 / 分母 | 违规率 |
|---|---:|---:|
| K03 签收早于揽收 | 23 / 96,475 | 0.02% |
| K04 状态与签收时间冲突 | 14 / 97,103 | 0.01% |
| C01 delivered 缺签收时间 | 8 / 96,478 | 0.01% |
| C02 履约状态缺审批时间 | 14 / 98,202 | 0.01% |

四条规则合计命中 59 次（未去重），对履约时效分析的影响小于 0.03% 订单。

**根因**：最可能是 ETL 时区转换或状态回写顺序问题；K04 与 C01 的少量重叠也提示状态机与时间戳由不同批次写入。

**证据**：`result/01-completeness.csv`、`result/02-consistency.csv`。

### P7 零值支付与异常商品尺寸（低）

**现象**：
- 支付金额 <=0：9 行（0.01%），其中 voucher 6 行、not_defined 3 行，金额合计 0.00，涉及 5+3 个订单。
- 商品重量/尺寸异常：4 个商品（0.01%），均属 `cama_mesa_banho`，重量为 0，尺寸 30×25×30 cm。

**影响面**：零值支付多为主支付行之外的拆分行，若直接用于客单价计算会轻微低估；4 个商品会让运费估算出现离群值。

**根因**：源系统占位值/录入缺失。零值支付集中在 voucher 与 not_defined，符合「占位行」特征；商品尺寸为 0 更像录入遗漏。

**证据**：`sql/04-accuracy.sql`（A02/A04）；`result/04-accuracy.csv`；`result/04-accuracy-2.csv`；`result/04-accuracy-3.csv`。

### 5.8 为什么有 20 条规则是 0 违规

32 条规则中有 20 条为 0，必须解释，否则无法判断是「数据干净」还是「规则太松」：

- **引用完整性（C03–C06）与主键/业务键（U01–U04、U06）**：全表扫描，0 孤儿、0 重复，说明这批结构性约束在快照上确实成立，不是抽样侥幸。
- **状态与时间（K02、K06）**：审批早于下单、答复早于创建均为 0，说明这两条顺序约束未被违反；相邻的 K03/K04 仍有少量违规，说明规则并非整体失效。
- **枚举与解析（V01–V03、V05、V07）**：状态、支付类型、UF 全部命中白名单，日期全部可解析，属于数据确实规范。
- **准确性（A01、A03、A05、A06）**：只能说明「没有负金额、评分越界、未来日期、分期越界」，不能说明金额与地址真实。A06 的上限 24 期是业务假设，规则本身偏宽，这是已知的规则局限性。

结论：0 违规主要来自数据干净与约束明确；准确性维度的 0 必须结合「未与权威库比对」一起读。

### 5.9 问题之间的关联（避免重复计数）

- **P2 与「每单多条评价」不是同一件事**：P2 是同一 `review_id` 跨多个订单（789/789 组跨订单），而 543 单 2 条、4 单 3 条评价是同一订单内不同 `review_id`，属于业务允许的一对多。两者互不覆盖，不能把「多评价订单」也算成重复。
- **P6 的四条规则会命中同一批订单**：C01（delivered 缺签收）与 K04（delivered 无签收）在定义上高度重叠，C02 与 K04 也可能交叉。因此 59 次命中是**规则命中次数**，不是 59 个唯一问题订单。
- **P1 与 P7 有少量交集**：9 条零值支付可能让对应订单的支付合计偏低，从而进入 K01 的 366 单；但 K01 的差额分布显示多数差异来自 1 元以上区间，零值支付只能解释很小一部分。
- **P3 与 P4 无重叠**：P3 是客户/卖家邮编长度，P4 是商品类目，分别落在不同表与不同规则上。
- 因此第 6 节的行数占比只能作为「规则命中量级」，不能当成「唯一问题记录数」；本报告没有声称 25,992 是去重后的坏行数。

严重度也不按行数排序：P3 命中 23,995 行但可通过补零确定性修复；P2 只有 814 行却破坏评论唯一键。前者是「面大但可逆」，后者是「面小但伤键」，所以两者都列为需要在上线前处置的问题。

## 6. 根因分析

### 6.1 归类结果

按 7 个问题条目的**主因**归类（一条问题只归一类），并给出各规则命中行数（未跨规则去重）：

| 根因类别 | 问题条目 | 条目占比 | 命中行数 | 行数占比 | 代表证据 |
|---|---|---:|---:|---:|---|
| 源系统录入 | P1、P5、P7 | 42.9%（3/7） | 501 | 1.9% | 金额双向差异、同人地址冲突、零值占位 |
| ETL 转换 | P2、P3、P6 | 42.9%（3/7） | 24,868 | 95.7% | review_id 跨订单重复、CEP 前导零、时间戳倒序 |
| 业务规则变更 | 无 | 0.0% | 0 | 0.0% | 无可用证据，不臆测 |
| 外部参照缺失 | P4 | 14.3%（1/7） | 623 | 2.4% | 翻译码表缺 2 个类目 |
| **合计** | **7** | **100%** | **25,992** | **100%** | — |

说明：条目占比是分析判断的计数，不是统计推断；行数占比是各规则分子之和，同一行可能被多条规则命中，未去重。两类占比不能互相替代。

### 6.2 逐类说明

**源系统录入（3 项，501 行）**

- P1 的金额差异双向存在（269 单支付多、97 单明细多），且只有 10 单含 voucher，说明不是单一的优惠券拆分规则；更像结算口径或分期手续费在源系统未回写到明细。
- P5 的同人地址冲突 122 组，既可能是搬家，也可能是录入不一致；在没有地址变更时间的情况下不能定论。
- P7 的零值支付集中在 voucher/not_defined，商品重量为 0 的 4 条记录同属一个类目，均符合「占位值/漏填」特征。

这三项的共同点是：**问题发生在数据进入管道之前**，靠 ETL 规则只能拦截，不能还原真值。

**ETL 转换（3 项，24,868 行）**

- P2：789 组重复 `review_id` 全部跨订单，且组内评分不冲突。这更像键生成/映射错误，而不是业务一对多；若是一对多，应是同一订单多条 review_id。
- P3：补齐前导零后 V04 违规率从 24.13% 降到 0.00%，直接证明是长度在转换中丢失，而非邮编本身非法。
- P6：时间戳倒序与状态冲突集中在 0.02% 以下，且状态与时间戳可能由不同批次写入，符合 ETL 时区/回写顺序问题的特征。

这一类占了命中行数的 95.7%，是**修复收益最高**的部分，因为多数可在管道内确定性修复（补零、重建键、统一时区）。

**业务规则变更（0 项）**

- 没有证据支持把任何一项归为业务规则变更。543 单有 2 条评价、4 单有 3 条评价，属于正常一对多，不计为缺陷。
- 明确写 0 项而不是勉强分配，是为了避免把「解释不了」包装成「业务变更」。

**外部参照缺失（1 项，623 行）**

- P4 的 610 条类目缺失与 13 条未翻译是两类问题：前者是上游没给值，后者是翻译码表没有跟上商品目录（`pc_gamer` 等新类目）。
- 外部参照缺失的修复方式与前三类不同：需要维护码表版本与对账机制，而不是改一条 SQL。

### 6.3 反事实检验：为什么这样归类

根因归类不是看名字猜，而是用「如果换成另一种原因，结果会怎样」来排除。以下四条检验都能在 `result/` 中找到对应输出：

| 检验 | 观察 | 支持的结论 | 排除的结论 |
|---|---|---|---|
| CEP 补零后重算 | 原始 V04 = 24.13%，LPAD 后 = 0.00%（`06-validity.csv` / `06-validity-2.csv`） | 字符合法、长度在转换中丢失 | 不是「邮编本身非法」，也不是源系统给出了错误号码 |
| review 重复组结构 | 789/789 组跨订单，0 组跨评分（`03-uniqueness-2.csv`） | 键映射/生成错误 | 不是同一订单的正常多条评价 |
| 金额差异构成 | 366 单中仅 10 单含 voucher、20 单多笔支付（`02-consistency-3.csv`） | 差异主要来自结算/录入口径 | 不能全部归因于优惠券拆分 |
| 类目缺失的列共现 | 610 个商品的类目、名称长度、描述长度、图片数同时缺失（`00-profile-2.csv`） | 整条商品记录不完整，属上游录入遗漏 | 不是单纯翻译表缺行；翻译表缺行只解释另外 13 条 |

补充一条反向检验：如果是 ETL 把金额算错，差异应集中在某个固定比例或固定方向；实际是 269 单支付多、97 单明细多，双向且分桶连续（54/160/131/21），更像源系统逐单录入/结算差异，而不是一条统一的转换公式出错。因此 P1 归「源系统录入」，不归「ETL 转换」。

### 6.4 根因与改进优先级的对应

- **先修 ETL**：影响 95.7% 的命中行，且修复确定性高（补零、review 键重建、时间统一）。
- **再治源系统**：金额与地址问题需要业务侧确认口径，技术侧只能做拦截与告警。
- **最后补参照**：类目翻译表更新成本低，但影响面小（2.4%），可排在其后。

### 6.5 根因判断的不确定性

这份归类回答的是「最可能的主因」，不是「已证实的唯一原因」，有三点必须说明：

1. **多因问题只归主因**。P5 的 122 组地址冲突，可能是搬家（业务事实变更），也可能是录入错误（源系统）；没有地址生效时间就无法区分。本报告把它归到「源系统录入」，是因为现有字段只能观察到冲突，不能证明哪一次填写是错的。若未来补上地址变更时间，这条可能改归「业务规则变更」。
2. **「业务规则变更」为 0 不等于不存在**。0 项的含义是「现有数据没有提供可区分的证据」，而不是「确定没有发生」。把无法解释的现象硬塞进这一类，会让根因分析看起来完整、实际不可信。
3. **行数占比会被大表放大**。P3 一条就占 24,868 行中的 23,995 行，使 ETL 类达到 95.7%；这不代表 ETL 有 95.7% 的工序出了问题，只代表这一条规则命中的记录多。修复优先级要同时看「可修复性」和「是否伤键」，不能只看行数。

因此，第 6 节的占比适合回答「先修哪一类」，不适合回答「哪一类错误更严重」，更不适合当作对外披露的统计口径。

## 7. 改进建议

分三层：约束层管「单行/单表能判的」，规则层管「跨表聚合能判的」，监控层管「趋势与超阈值」。三层缺一不可：只有约束会漏掉跨表问题，只有规则会等到批处理才发现，只有监控则没有阻断能力。

### 7.1 约束层：能进数据库约束的，不要留给脚本

| 表 | 建议约束 | 当前实测 | 上线策略 |
|---|---|---|---|
| orders | `customer_id` 外键 → customers | 孤儿 0（C06） | 可直接启用 |
| order_items / payments / reviews | `order_id` 外键 → orders | 孤儿均 0（C03–C05） | 可直接启用 |
| orders / customers / products | 主键唯一 | 重复 0（U01/U02/U06） | 可直接启用 |
| order_items | `UNIQUE(order_id, order_item_id)` | 重复 0（U03） | 可直接启用 |
| payments | `UNIQUE(order_id, payment_sequential)` | 重复 0（U04） | 可直接启用 |
| reviews | `UNIQUE(review_id)` | **重复 814 行** | 先隔离/修复 789 组，再启用 |
| payments | `CHECK (payment_value > 0 OR payment_type IN ('voucher','not_defined'))` | 9 行零值均属这两类 | 可直接启用，允许合法占位 |
| products | `CHECK (product_weight_g > 0 AND product_length_cm > 0 AND product_height_cm > 0 AND product_width_cm > 0)` | 4 行零值 + 2 行空值 | 先隔离 4 行，再启用 |
| customers | 入仓时 `LPAD(zip, 5, '0')` 后 `CHECK` 五位数字 | 补齐后违规 0（V04-canonical） | 在 staging 层补齐，不改原始快照 |
| orders | `CHECK (order_status IN (...8 种...))` | 越界 0（V01） | 可直接启用 |
| payments | `CHECK (payment_type IN (...5 种...))` | 越界 0（V02） | 可直接启用 |
| customers / sellers | `CHECK (state IN (...27 个 UF...))` | 越界 0（V03/V07） | 可直接启用 |
| reviews | `CHECK (review_score BETWEEN 1 AND 5)` | 越界 0（A03） | 可直接启用 |

要点：
- **CEP 不在原始层改值**。原始快照保持可追溯，在 staging 视图做 `LPAD`，约束建在 staging 上。
- **review_id 的唯一约束不能直接加**。先按 789 组隔离，确认是键映射错误后重新生成 `review_id`，再加约束；直接加会导致整批装载失败。
- 金额勾稽、同人地址冲突这类**跨表/跨行**问题无法用单表 CHECK 表达，必须进规则层。

### 7.2 规则层：把 32 条 SQL 变成规则资产

现状是「32 条脚本 + 人工看 CSV」。要持续跑，需要把规则登记到表，由调度器执行、结果落历史表。

**规则登记表**：

```sql
CREATE TABLE dq_rule (
  rule_id        VARCHAR(32) PRIMARY KEY,
  dimension      VARCHAR(16) NOT NULL,   -- completeness/consistency/uniqueness/accuracy/timeliness/validity
  target_table   VARCHAR(64) NOT NULL,
  rule_name      VARCHAR(200) NOT NULL,
  rule_sql       TEXT NOT NULL,          -- 返回 numerator, denominator 的只读 SQL
  threshold_pct  DECIMAL(6,3),           -- 违规率上限，NULL 表示只记录不告警
  severity       VARCHAR(8) NOT NULL,    -- BLOCK/WARN/INFO
  owner          VARCHAR(64),            -- 规则责任人（角色，不写个人）
  enabled        BOOLEAN NOT NULL DEFAULT TRUE,
  updated_at     TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

| 字段 | 作用 |
|---|---|
| `rule_id` | 与 `sql/` 文件名中的规则编号一致（C01、K01……），保证报告可回溯 |
| `dimension` | 六维之一，用于按维聚合得分 |
| `target_table` | 主表，便于按表定位责任人 |
| `rule_sql` | 统一返回 `numerator, denominator`，执行器只做一件事：算比率 |
| `threshold_pct` | 违规率阈值；阈值不是行业标准，需按基线校准 |
| `severity` | `BLOCK` 阻断装载、`WARN` 生成工单、`INFO` 仅记录 |
| `owner` | 角色（如 data-owner-etl），不写个人姓名 |
| `enabled` | 规则开关，避免历史规则长期失效仍占位 |

**执行结果表（用于趋势与审计）**：

```sql
CREATE TABLE dq_run (
  run_id        VARCHAR(40) NOT NULL,
  rule_id       VARCHAR(32) NOT NULL,
  run_at        TIMESTAMP NOT NULL,
  numerator     BIGINT,
  denominator   BIGINT,
  violation_pct DECIMAL(8,4),
  passed        BOOLEAN,
  snapshot_ts   TIMESTAMP,
  PRIMARY KEY (run_id, rule_id)
);
```

**迁移方式**：
1. 把现有 32 条规则逐条登记，`rule_sql` 直接取对应 SQL 的主体。
2. 首次以 `severity=INFO` 跑一周，用实测分布校准 `threshold_pct`。
3. 校准后再把结构性规则（孤儿、主键、枚举）升为 `BLOCK`，统计类规则保持 `WARN`。
4. 每日装载后调度；`BLOCK` 失败则停止向下游发布，`WARN` 失败生成工单并带违规样本。

**本报告不声明修复后的违规率**。第 5 节的数字是修复前基线；「由 a% 降至 b%」必须在执行修复后用同一套 SQL 重跑才能写，当前没有这次重跑。

### 7.3 监控层：阈值告警与趋势

建议的初始阈值（按本次基线校准，不是行业标准）：

| 规则 | 指标 | 建议阈值 | 级别 | 动作 |
|---|---|---|---:|---|
| C03–C06 | 引用完整性孤儿率 | >0% | BLOCK | 停止发布，回查上游批次 |
| U01–U04、U06 | 主键/业务键重复率 | >0% | BLOCK | 停止发布，隔离重复键 |
| U05 | review_id 重复率 | >0% | BLOCK | 阻断，重建评论键 |
| V04 | 原始 CEP 非 5 位比例 | >1% | BLOCK | 检查导出类型是否又退化为整数 |
| K01 | 金额勾稽不符率 | >0.50% | WARN | 生成对账工单，附差额 Top20 |
| C07 | 商品类目缺失率 | >2.00% | WARN | 通知商品域补录 |
| V06 | 类目未翻译率 | >0.10% | WARN | 更新翻译码表 |
| K03+K04 | 时间/状态冲突率 | >0.10% | WARN | 检查时区与回写顺序 |
| A02 | 零值支付比例 | >0.05% | WARN | 检查支付拆分逻辑 |
| A04 | 异常重量/尺寸比例 | >0.05% | WARN | 通知商品域修正 |
| 新鲜度 | `now − max(event_time)` | >7 天 | BLOCK | 检查上游是否停更（需先补入库时间字段） |

**监控层要解决的是「这次查完，下次还会不会坏」**：
- 每次运行写 `dq_run`，按规则看 7 日/30 日趋势，而不是只看单次是否过线。
- 告警必须带**可复现证据**：规则 ID、快照时间、分子/分母、样本主键前 N 条。
- `BLOCK` 与 `WARN` 的责任人不同：前者是管道 owner，后者是数据域 owner，避免所有告警都落到同一人。
- 阈值每季度复核一次；数据分布变化后，旧阈值会失去意义。

### 7.4 实施顺序与验收标准

修复不能一次全上，否则出了问题无法区分是哪一步引入的。建议按以下顺序，每一步都用同一套 32 条规则重跑并留证。

| 阶段 | 动作 | 验收标准 | 验收证据 |
|---|---|---|---|
| 1. staging 修复 | CEP 补零；review 键重建；时间戳统一时区 | V04 原始口径仍如实记录、canonical 口径为 0；U05 为 0；K03/K04 不高于基线 | 重跑后的 `06-validity*.csv`、`03-uniqueness*.csv`、`02-consistency.csv` |
| 2. 约束启用 | 先启用孤儿/主键/枚举类约束，再启用 review 唯一与商品尺寸 CHECK | 负向插入测试被拒绝；正常批次可装载；C03–C06、U01–U04/U06 保持 0 | 约束定义 + 负向测试记录 + `01`/`03` 输出 |
| 3. 规则登记 | 32 条规则写入 `dq_rule`，先以 INFO 跑基线 | 一次调度产生 32 条 `dq_run` 记录；同一快照重跑结果一致 | `dq_run` 查询结果 + 结果 CSV |
| 4. 监控上线 | 按 7.3 阈值配置 BLOCK/WARN，接入工单 | BLOCK 演练能停止发布；WARN 工单包含规则 ID、分子/分母、样本主键 | 告警演练记录 |

**验收不以「综合分上升」为唯一标准**。综合分是加权平均，可能被四个高分维度掩盖一个伤键问题；验收必须逐条看 P1/P2 是否闭环。若某条规则修复后仍超阈值，保留 WARN 并登记，不允许把阈值调高来「变绿」。

**回滚原则**：原始快照只读，所有修复在 staging 或下游版本完成；规则包与数据版本分别编号，出现问题时可以回退规则包而不动数据。

**前后对比要求**：修复前后必须固定同一快照与同一规则包，输出逐规则对照表；否则无法区分「修复有效」与「换了一批数据」。

### 7.5 规则执行器的契约

把 32 条脚本搬进 `dq_rule` 之前，先固定执行契约，否则每条 SQL 各写各的，调度器无法统一处理：

| 契约项 | 要求 | 原因 |
|---|---|---|
| 返回列 | 必须且只能返回 `numerator`、`denominator` 两列，均为非负整数 | 执行器只做 `numerator / denominator`，不解析业务字段 |
| 分母为 0 | 返回 0 行或 `denominator = 0` 时记为 `N/A`，不记 0 分 | 避免「没有可比记录」被误判为「完全合规」 |
| 只读 | 规则 SQL 只能 SELECT，禁止临时表、INSERT、UPDATE | 防止质量检查反过来改数据 |
| 确定性 | 同一快照、同一规则包，重复执行结果一致 | 否则无法做趋势与复现 |
| 时间口径 | 统一按 UTC 存储与比较；展示层再转本地时区 | 避免 P6 这类时区倒序问题在规则层重现 |
| 样本输出 | 规则可选返回违规样本主键（前 20 条），单独落表 | 告警要能直接定位，而不是只给一个比率 |
| 版本绑定 | 每条 `dq_run` 记录 `rule_pack_version` 与 `snapshot_ts` | 报告数字要能指回具体规则版本与快照 |

执行器伪代码只有三步：读 `enabled=TRUE` 的规则 → 执行 `rule_sql` → 按 `threshold_pct` 与 `severity` 写 `dq_run` 并决定是否阻断。这样新增规则只需插一行，不需要改调度代码。

另一个容易忽略的点是**不要在规则 SQL 里硬编码报告日期或快照时间**。像 A05（未来日期）和及时性检查都依赖「当前时点」，应作为参数由执行器注入；否则每隔一段时间就要改 SQL，规则也就失去了可复现性。

### 8.3 质量分级

分级只看**可评分维度**，准确性因「仅部分可判定」不单独作为升级依据；任一维度低于门槛即降级。

| 等级 | 判定条件 | 适用场景 |
|---|---|---|
| **Gold** | 五个可评维度均 ≥99.50，且无未闭环的高/中问题 | 面向客户的核心分析、计费对账 |
| **Silver** | 五个可评维度均 ≥98.00，且无未闭环的高问题 | 一般分析、报表 |
| **Bronze** | 五个可评维度均 ≥95.00，问题已登记且有修复计划 | 探索性分析、内部建模 |
| 不合格 | 任一维度 <95.00，或存在未登记的高问题 | 不对外供给 |

**本快照评级：Bronze（铜级）**。理由：有效性 96.55 低于 Silver 门槛 98.00；一致性 99.25、唯一性 99.86、完整性 99.73 均高于 Silver 门槛，但 P1/P2 两个高问题未闭环。若完成 CEP 补齐与 review_id 去重，可重新评级；**本次未做修复后重跑，不声明升级结果**。

## 9. 局限与未覆盖

1. **准确性未与权威库比对**：地址、金额、商品属性的「真实值」无法验证；本报告的准确性只覆盖负值、越界、未来日期等规则可判定部分。
2. **及时性不可测**：缺入库时间字段；4.6 的审批时长是业务处理时长，快照年龄是数据陈旧度，两者都不能替代「事件→入库」延迟。
3. **快照时间跨度有限**：2016-09 至 2018-10，且距报告日 8.1 年；结论描述的是该快照，不是当前市场。
4. **未纳入 geolocation 表**：没有经纬度，未做坐标合法性、CEP→坐标映射、区域一致性校验。
5. **规则口径会影响结论**：V04 主口径为原始 5 位，若改为「补零后再校验」，有效性会从 96.55 上升（V06 仍为 0.04%），综合分随之变化。本报告采用更严格的主口径，并同时公开敏感性口径。
6. **维度内等权、维度间权重自设**：换权重会改变综合分的绝对值；报告的用途是排序改进优先级，不是给数据集发「行业排名」。
7. **未执行修复后重跑**：第 7 节是建议，不是已验证的修复效果；任何「降至 b%」的说法都需要复测。
8. **未分析评论文本语义**：评论标题/正文缺失率高，但不判断内容质量与真实性。
9. **单机离线环境**：DuckDB 全表扫描，未评估并发、吞吐、增量更新；生产环境的性能与调度需要另行验证。
10. **许可限制**：CC BY-NC-SA 4.0，公开引用可以，商业使用与闭源再分发不可以。
